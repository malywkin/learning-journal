# День 18 — Планировщик и фоновые задачи (шпаргалка)

Тема: MCP-инструмент с отложенным/периодическим выполнением; собирает данные, делает это
по расписанию, отдаёт агрегат. Цель — ассистент, который «работает 24/7 и периодически
выдаёт сводку». У нас: сервер по часам сам ходит в Reddit (твой `arctic` / Arctic Shift),
копит посты в SQLite, сворачивает их LLM в дайджест.

Сквозной образ: **ресторан**. День 17 — официант (реактивный сервер: отвечает на заказ).
День 18 — рядом встал **повар с будильником** (планировщик): сам по часам варит и пишет сводку.

## Что собрано (код, всё проверено вживую)
- `arctic.py` — вендорная копия твоего reddit-клиента (без ключей, публичный архив).
- `collector.py` — три «работы»: `collect_subreddit` (сбор → SQLite, без дублей),
  `make_digest` (LLM-сводка, temp 0, запрет выдумывать), `collect_and_digest` (разовое
  отложенное дело: один раз собрать и сразу свернуть).
- `scheduler.py` — APScheduler 3.11: расписание на диске, защиты от дублей/лавины.
- `mcp_server.py` — FastMCP-сервер, планировщик поднят в его lifespan; инструменты
  `schedule_collection / schedule_digest / schedule_once / run_now / list_jobs / get_digest /
  get_status / cancel_job`.
- `app.py` + `index.html` — тёмная витрина-«капот» (язык Дня 17): каждый тик повара —
  анимированная цепочка шагов, что загорается по очереди.
- CLI — `task18.py` (`--demo` и интерактив). Запуск витрины — `python run.py` → :8019.

## Три узла (суть, без зубрёжки ручек)

### 1. «24/7» = расписание лежит на диске + результат забираешь сам (pull)
- «24/7» не про «процесс никогда не падает», а про то, что **расписание переживает остановку**.
- Будильники записаны в книжку на диске (jobstore — отдельный sqlite-файл). Перезапуск →
  повар открывает книжку и заводит всё заново. Держать расписание «в голове» (в памяти
  процесса) — потерять его при первом же рестарте.
- Повар не бегает за тобой: кладёт готовое в **журнал** (SQLite), ты **забираешь** сам, когда
  смотришь (витрина опрашивает). Сервер не «пушит». **Pull — источник истины, push — в лучшем
  случае ускорение** (из него можно выпасть, если отвернулся).

### 2. Надёжность по-взрослому — один вопрос вместо пяти ручек
Запоминать пять настроек не нужно. Все они отвечают на **один вопрос: что делать, когда жизнь
пошла не по расписанию?** (мир грязный: рестарты, простой, затянувшаяся задача).
- перезапустились → **не плоди копии** (у задачи есть имя + «заменить», `replace_existing`);
- проспал кучу тиков → **не делай всё разом** (схлопнуть, `coalesce`);
- опоздал чуть — прости, сильно — пропусти (`misfire_grace_time`);
- прошлый ещё крутится → **не лезь вторым** (`max_instances=1`).

Наивный `while True: sleep` не умеет ничего из этого — потому берут готовый планировщик.

**Линза для разбора чужих решений:** «а они подумали про **перезапуск / простой / нахлёст**?»
Подумали — взрослое решение, нет — игрушка.

Две «когда»: **`interval`** — «через каждые N» (отсчёт от прошлого раза); **`cron`** — «по
времени дня» (в 9:00, по будням). «Каждый день в 9» — это cron; поставить интервалом 24ч —
поедет дрейфом.

### 3. MCP Tasks — это НЕ планировщик
- **MCP Tasks** (`task=True`, новинка спеки 2025-11-25) — «позвони сейчас, забери потом» для
  **одной долгой** работы. Номерок: запрос → id → позже забрал результат. Один раз, без повтора.
- **Планировщик** — про **повтор и время**, живёт **вне** протокола MCP (наша пристройка сбоку).
- Оси: Tasks = «долго, но один раз»; планировщик = «снова и снова по будильнику».
- Точный факт: **в самом MCP расписания нет** — нет кирпичика «каждый день в 9». Кто говорит
  «MCP-инструмент сам по расписанию» — расписание у него в своём планировщике, не в MCP.

## А как по-взрослому (лестница зрелости)
1. **In-process планировщик** (наш APScheduler) — для малого масштаба, дефолт.
2. **Внешний cron / systemd-timer** — расписание вынесено из приложения в ОС.
3. **Durable execution** (Temporal, DBOS, Restate) — когда задача обязана пережить краш
   ровно один раз (exactly-once) и сама возобновиться с места падения.
- Протокольный вариант фоновой работы — `task=True` (FastMCP 2.14+); чтобы пережить рестарт —
  на бэкенде Redis, а не эфемерной памяти. Это для «одной долгой», не для расписания.

## Один тонкий момент (можно не держать, но знать)
Фоновая работа не должна **морозить** сервер: тяжёлый/сетевой кусок — в стороне (отдельный
поток / `await`), иначе сервер перестанет отвечать на запросы и оборвётся по таймауту.
