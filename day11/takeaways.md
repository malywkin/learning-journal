# День 11 — модель памяти ассистента (memory layers). Шпаргалка

## Одна картинка

```
                    реплика пользователя
                            │
         ┌──────────────────┼───────────────────┐
         ▼                  ▼                    ▼
   КРАТКОСРОЧНАЯ        РОУТЕР (код)         (на чтении)
   диалог, дословно   2 развилки:           сборщик запроса
   окно последних N   1) есть что сохранять?  выбирает, какие
   падает БЕЗ решения  2) задача или человек?  слои подмешать
         │                  │  │                    │
         │          ┌───────┘  └───────┐            ▼
         │          ▼                  ▼         в модель → ответ
         │     РАБОЧАЯ            ДОЛГОВРЕМЕННАЯ
         │   данные задачи        профиль человека
         │   (бюджет, стек,       (стиль, постоянные
         │    дедлайн)             запреты, роль)
         │   живёт = пока          переживает задачу
         │   жива задача            и сессию
         └──── всё хранится ОТДЕЛЬНО (свой файл на слой) ────┘
```

## Концепты

- **Память — свойство обвязки, не модели.** Модель stateless; «помнит» наш код, заново
  подавая нужные данные в каждый запрос. День 11 — как эти данные разложить.
- **Три слоя = три срока жизни.** Краткосрочная — «прямо сейчас» (диалог). Рабочая —
  «по этой задаче» (умрёт с задачей). Долговременная — «про человека» (живёт всегда).
- **Тест на отличие рабочей от долговременной:** «пригодится ли факт в СЛЕДУЮЩЕЙ, не
  связанной задаче?» Да → долговременная. Нет → рабочая.
- **Краткосрочная vs рабочая:** краткосрочная — сырой диалог дословно (что только что
  сказали), рабочая — извлечённые решения по задаче (что мы установили). Реплика про
  REST лежит секунду в краткосрочной, а как решение оседает в рабочей.
- **Роутер — самое хрупкое место.** Краткосрочной он не нужен (кладём всё подряд).
  Рабочей и долговременной нужен: две развилки на каждую реплику. Граница «задача или
  человек» размытая — на краях ошибается.
- **«Явно выбираем, что и куда» = решает КОД.** Модель лишь предлагает факты в
  размеченные секции (`=== РАБОЧАЯ === / === ДОЛГОВРЕМЕННАЯ ===`), а раскладывает их по
  отдельным слоям наш код (`parse_router_output` → `working.set` / `longterm.set`).
- **Хранятся отдельно.** Каждый слой — свой файл (диалог → json, карточки → txt).
  «Новая задача» обнуляет рабочую и диалог, долговременную оставляет — вот зачем разделять.
- **Влияние слоя = сторона чтения.** Что подмешали в запрос — то и изменило ответ.
  Полный профиль в каждый запрос не тащим (антипаттерн «всё в один промпт»).

## Живые цифры (gpt-oss-20b, реальный OpenRouter)

- Роутинг по слоям отработал чисто: профиль (роль, стиль, запрет RxJava) → долговременная;
  стек/бюджет/дедлайн → рабочая; «окей, спасибо» → никуда.
- Влияние профиля (новая сессия, диалог пуст, профиль только в долговременной):
  **с профилем — 389 символов, без таблицы**; **без профиля — 2770 символов, с таблицей**.
  Семикратная разница на одном вопросе — слой реально меняет ответ.
- Грабля вживую: при переэмитировании карточки слабая модель **перевела ключи** на
  английский («роль» → «role») → ложная трасса «добавлено в долговременную». Лечится
  guardrail «копируй прежние поля буква в букву, не переводи ключи» + temperature 0.

## Что считается устаревшим / переоценённым (бриф 2026)

- Классы памяти старого LangChain (`ConversationBufferMemory` и пр.) — удалены, ушли
  в `langchain-classic`. Замена — LangGraph checkpointer (сессия) + store (между сессиями).
- «Слать всю историю целиком» каждый ход — дорого и хуже по качеству (боль Дней 8–9).
- Маркетинг «экономия 90%» (сравнение с голой полной историей — соломенное чучело),
  «граф всегда лучше вектора» (бенчмарки смещены: position/length bias).
- На простых задачах аккуратный плоский поиск не хуже трёх-слойной машинерии (Hu et al.,
  2026) — слои оправданы для кросс-сессионности и длинных историй, не «всегда».
- Честно про термины: «краткосрочная ≠ рабочая» в настоящей психологии памяти; мы берём
  эти слова как удобные инженерные ярлыки, не как нейробиологию.

## Где это в индустрии

- Letta/MemGPT: core (в окне) / recall (искомая история) / archival — тот же расклад.
- LangGraph: checkpointer = краткосрочная (сессия), store = долговременная (кросс-сессия).
- Anthropic memory tool, mem0, Zep — структурированные поля/факты, а не проза-пересказ
  (поэтому карточка, а не «справка»). Фронтир: временны́е графы, фоновая консолидация.

## Проверь себя (закрой ответы)

1. Почему краткосрочной памяти роутер не нужен, а рабочей и долговременной — нужен?
   → краткосрочной нечего решать (кладём всё подряд, режем старое); там, где есть выбор
     «сохранять ли» и «куда», нужен роутер.
2. «Для этой фичи хватит REST» — какой слой? А «я всегда пишу тесты на pytest»?
   → рабочая (решение по задаче) / долговременная (привычка человека).
3. В чём «явно выбираем, что и куда» технически? → решение о слое принимает КОД, разобрав
   размеченный ответ модели; модель только предлагает факты.
4. Почему для честной проверки влияния долговременной памяти диалог надо очистить?
   → иначе факты профиля видны модели прямо из окна диалога, и слой ни при чём; нужно,
     чтобы факт жил ТОЛЬКО в долговременной.
5. Что делает «новая задача» и почему это и есть смысл разделения слоёв?
   → чистит рабочую и диалог, оставляет профиль: задача в архив, человек остаётся.
