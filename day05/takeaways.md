# День 5 — Версии моделей · конспект для повторения (A + B + C)

> Шпаргалка по трём узлам дня. Можно подсматривать; пригодится для retrieval-повторения.
> Цифры в примерах — с наших живых прогонов на OpenRouter (gpt-oss), июнь 2026.

## Одна картинка: «слабее/сильнее» = ДВЕ оси, не линейка
- **Ось A — какая модель** (свойство обученной модели). Аналогия: *кого нанял* (джуниор/партнёр).
- **Ось B — сколько ей дали думать** (reasoning effort / test-time compute). Аналогия: *сколько дал времени на ответ*.
- Оси **ортогональны**: мелкая модель с большим think-бюджетом обходит крупную, отвечающую сразу. Но **«дольше ≠ лучше»** (overthinking).
- Чистый разделитель осей: *модель та же или другая?* + *куда ушли токены — в видимый ответ или в думанье?*

---

## A — «сила модели»: почему «число параметров» врёт

1. **Две оси, ортогональны; «дольше ≠ лучше».** Overthinking реален: больше reasoning может **снизить** точность.
2. **Причина №1 — архитектура (MoE).** Модель из «экспертов»; router на каждый токен поднимает лишь несколько, и **каждый раз других** из общего пула.
   - **total** (напр. 120B) = ёмкость знаний / потолок качества; **active** (напр. 12B) = цена и скорость на запрос.
   - В имени: `...-120b-a12b` → 120B всего, активных 12. «Больше параметров» ≠ «дороже/медленнее».
3. **Причина №2 — данные + пост-тренировка.** «Параметры» = пустой объём. Данные (чем наполнили: чистый «учебниковый» корпус vs сырой веб) и пост-тренировка (instruction tuning + RLHF + reasoning-тренировка) делают мелкую свежую модель сильнее старой большой. *Phi-3.5 3.8B > Llama-3.1 8B; Qwen3-4B ≈ Qwen2.5-72B.* Пост-тренировка — где **вшивают** умение рассуждать (мост к оси B).
4. **Dense ещё жив:** фокус MoE «знать как большая, считать как маленькая» оплачен **памятью** — все эксперты грузятся в VRAM. Где узкое место память (телефон/edge/слабый GPU) — dense выигрывает (+ проще обслуживать/дообучать).
5. **«Ресурсоёмкость» — не одно число.** MoE экономит вычисления, тратит память; dense наоборот. «Легче» = всегда «легче по чему». Для API-моделей (мы не хостим веса): меряем latency / токены / цену, а не VRAM.
6. **Устарело:** «параметры = сила»; «позиция в списке HuggingFace = сила» (HF Open LLM Leaderboard закрыт 13.03.2025; `huggingface.co/models` — каталог по популярности). MMLU как разделитель (насыщен) → GPQA Diamond, SWE-bench, LMArena Elo, AA Intelligence Index. Наивный model-swap без контроля переменных.

**3 причины, почему 4B-модель Q может бить 70B-модель P:** (1) данные, (2) пост-тренировка (умение рассуждать), (3) ось B — Q дали больше думать. «Умеет рассуждать» (A) ≠ «дали рассуждать сейчас» (B).

## B — «как честно мерить» скорость/токены/цену

**B-1 — скорость = ДВА числа.** Время = фаза 1 (молчит/думает) + фаза 2 (печатает).
- **TTFT** (до первого видимого токена) ≠ **total**. У reasoning-моделей TTFT 10–150с — это *думанье*, не «медленный сервер».
- **output speed** = `токены / (total − TTFT)` — скорость печати, не общая. Когда думанье съело почти всё время, метрика взрывается (наш `2802 tok/s`) → помечаем `think`.
- В коде: `stream=True`, засечь время **первого** чанка (TTFT) и **последнего** (total). Без стрима — только total.

**B-2 — токены: квитанция `usage`.**
- `prompt_tokens` (вход) · `completion_tokens` (выход) · `total_tokens` = сумма.
- У reasoning: `completion_tokens_details.reasoning_tokens` — **невидимое** думанье. **`completion = видимый ответ + reasoning`** (проверено: `total = prompt + completion`, `reasoning ⊆ completion`).
- **Ловушка:** текст думанья скрыт, но reasoning-токены **посчитаны и оплачены** по выходному тарифу. Длина ответа на экране ≠ за что платишь (короткий ответ может стоить дороже).
- Не каждый провайдер отдаёт `reasoning_tokens` корректно (видели кривой стрим-сплит у free) → надёжно считать выход как **`total − prompt`**.

**B-3 — цена = токены × тариф (тарифа два).**
- `цена = prompt/1e6 × тариф_входа + выход/1e6 × тариф_выхода`. Тариф — за **1M** токенов.
- **Выход дороже входа** (в неск. раз) **и** объёмнее → **доминирует** (в примере выход = ~99% счёта).
- **Punchline:** ты управляешь входом, а объём выхода диктует модель (особенно скрытое думанье). «Спрошу покороче, чтоб сэкономить» — не работает.
- **Кэш входа** (`prompt caching`): тот же начальный кусок промпта → ~10× дешевле.

**Что увидели на живом прогоне (ось B, gpt-oss-20B):**
| effort | TTFT | reasoning-токены | ~цена |
|---|---|---|---|
| low | ~4с | ~70 | $0.00006 |
| medium | ~19с | ~890 | $0.00020 |
| high | ~31с | ~1390 | $0.00033 |

effort вверх → TTFT и reasoning-токены **взрываются**, цена ×5.5. Бонус: `max_tokens` у gpt-oss «мягкий» (не ограничил выход).

## C — качество без обмана (LLM-судья)

**C-1 — «распечатать 3 ответа» ≠ сравнение.** Глазами — субъективно/невоспроизводимо/не масштабируется/без числа. Качество надо превратить в **оценку по записанной рубрике**. Человек — эталон; модель-судья даёт масштаб + число. Ценность = **вынести критерии из головы наружу** (потом можно судить самому ИЛИ делегировать).

**C-2 — перекосы судьи и лечение:**
- **Position bias** (любит первый слот) → **swap-and-agree**: судить в оба порядка, засчитывать только при совпадении; перевернулось → ничья.
- **Verbosity bias** (любит длинные) → рубрика «награждай краткость» + шкала.
- **Self-preference** (любит свою семью) → судья = отдельная модель.
- swap = контроль переменной: меняем только порядок; сдвинулся вердикт → судили порядок, не качество.

**На живом прогоне:** swap-and-agree поймал position bias (2 ничьи на перевороте); `medium vs high` устойчив. Эмпирически подтвердило overthinking из оси A.

## Чек-лист сильного решения дня (что отличает от «напечатал 3 ответа»)
1. **Один запрос фиксирован**, меняем по одной переменной (ось A: размер; ось B: effort).
2. Меряем **три раздельных числа**: TTFT / output speed (или total) / `usage` (вход-выход-reasoning).
3. «Стоимость» бесплатных моделей = $0 → меряем **токены** + «как бы цена» по реальному тарифу.
4. Качество = **LLM-судья** с **swap-and-agree** + рубрика «краткость» + судья ≠ участник.
5. **Повторные прогоны** (медиана) против free-tier шума.
6. Честно помечать артефакты: `think`-bound скорость, кривой стрим-сплит, мягкий `max_tokens`, rate-limits.
