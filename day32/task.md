# День 32. Автоматизация ревью кода

Настройте пайплайн, в котором ассистент анализирует новый PR.

Ассистент должен:
- получать diff и изменённые файлы;
- использовать RAG (документация + код);
- выдавать текст ревью.

Минимальный результат:
- пайплайн (например GitHub Action) запускается на PR;
- ассистент получает diff;
- возвращает: потенциальные баги, архитектурные проблемы, рекомендации.

Результат: автоматическое AI-ревью кода.
Формат: видео + код.

---

## Как собрано (наше решение, поверх Дня 31)

Труба из §12-13 конспекта: `PR открыт → diff → RAG (доки+код) → ревью → комментарий в PR`.

- `ai-review.yml` (в `Tasks/.github/workflows/`) — TRIGGER: запускается `on: pull_request`,
  выдаёт токену права `pull-requests: write`, ставит Python, гоняет `ai_review.py`.
- `ai_review.py` — ядро: берёт diff (`gh pr diff`), добирает контекст (правила проекта +
  доки дня + код рядом), зовёт модель на структурное ревью (баги/архитектура/рекомендации),
  кладёт один комментарий в PR (правит свой прошлый, а не плодит — против спама).
- `review_llm.py` — мотор запроса (переиспой Дня 31): DeepSeek → OpenRouter, retry→fallback
  (§14), структурный ответ через `json_object` (грабля Дня 24).
- `REVIEW_GUIDE.md` — «брендбук»: правила проекта, с которыми сверяется ревью.
- Локальный режим `--diff файл` — smoke test (§16): печатает ревью, ничего не постит.

Ненадёжность модели (§14): её сбой НЕ роняет сборку и НЕ мешает влить PR — ревью это
рекомендация, а не запрет.
