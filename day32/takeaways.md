# День 32 — Best practices: AI-ревью кода как пайплайн на PR

Памятка на будущее: как собрать (и до чего дотянуть) робота, который сам ревьюит PR.
Три слоя источников помечены: **[Л §]** — лекция Гладкова (конспект недели 7), **[brief]** —
наша разведка обвязки GitHub (первоисточники), **[поток]** — что делают верхи потока
(разбор `Analysis/by-day/day32/analysis.md`, 35/37 решений).

---

## 1. Скелет пайплайна (минимум, чтобы тема была закрыта)
**[Л §12–13]** `TRIGGER → INPUT → AGENT → OUTPUT`:
`PR открыт → берём diff → добираем контекст (доки + код) → структурное ревью → комментарий в PR`.

Задание закрывается **не** «вызовом модели по diff», а **замкнутой петлёй**: если нет запуска
на реальном PR и/или нет постинга ответа назад — закрыта только левая половина, правая провалена.

## 2. Обвязка GitHub — обязательное (без этого молча не работает)
- **[brief]** Триггер: `on: pull_request` с `types: [opened, synchronize]` (synchronize = новый пуш в PR).
- **[brief]** Права ЯВНО: `permissions: { contents: read, pull-requests: write }` — с 2023 токен по
  умолчанию read-only, без этого блока постинг падает.
- **[brief]** diff проще всего: `gh pr diff <N> --patch` (gh предустановлен на раннере; нужен env
  `GH_TOKEN`). Для точных позиций строк под inline — из PR API (`git diff base...head`, three-dot).
- **[brief]** Ключ модели — секрет репозитория (`${{ secrets.* }}`), НИКОГДА не в коде; в логах маскируется.
- **[brief]** Свежие мажоры экшенов: `actions/checkout@v7`, `github-script@v9` (Node 24). `set-output`,
  `artifact@v3` — мертвы.

## 3. Устойчивость к сбою модели — ГЛАВНЫЙ водораздел зрелости
**[Л §14]** нейронка ненадёжна → её сбой НЕ должен ронять CI и НЕ должен пушить мусор.
**[поток]** это провалили даже 8 сильных решений (`exit 1` без ретраев) — самый частый дефект.
- **Retry** до 3 попыток (прогрессивный backoff) на сеть/таймаут/мусорный ответ.
- **Fallback**: другая модель / эвристики / деградация при пустом контексте — прописанные, не «залогировал и всё».
- **Никогда не валим сборку из-за модели:** `exit 0` / `if: always()` + короткий fallback-комментарий.
  Ревью — рекомендация, финальное слово за человеком (**[Л §14]** human-in-the-loop).
- *Наш День 32:* `review_llm.ask_json` — retry→fallback DeepSeek→OpenRouter, при полном провале `None`
  и job не падает.

## 4. Против спама — идемпотентный комментарий (делают только верхи)
**[поток]** на каждый push бот не должен плодить дубли. Держи в теле скрытый маркер
(`<!-- ai-review-bot -->`), при повторе — найди свой прошлый комментарий и **обнови (PATCH)**, а не
добавляй новый. *Наш День 32:* сделано через `gh api ... issues/comments` + метка.

## 5. Против галлюцинаций — проверять находки против diff (мост к Дню 24)
**[поток]** сильнейшие не доверяют модели на слово:
- Находка идёт inline, только если её `(файл, строка)` **реально есть в diff**; невалидные — в общую сводку.
- Цитата проверяется как **дословная подстрока** diff; номер строки пересчитывается по ADDED-строкам
  кодом, а не берётся у модели (Rogovoy).
- Топ (Ионов) — **второй проход модели-аудитора**: по каждой находке CONFIRMED/REJECTED + фильтр
  самоопровержений.
- **Это дословно наш приём Дня 24** (проверка цитат подстрокой + судья faithfulness) — переиспользуемо
  один-в-один. Наш День 32 этого пока НЕ делает — очевидный следующий шаг.

## 6. Inline-замечания на строки (сверх задания)
**[поток]** вместо одного сводного блока — замечания на конкретные строки через
`pulls.createReview` (`side: RIGHT`, `line`; `position` устарел). Читается как настоящее ревью.

## 7. Контекст / RAG под CI
- **[brief/поток]** НЕ грузить весь репозиторий (дорого, окно, промахи). Diff как ядро + добор нужного.
- **Под облако** — лёгкий путь оправдан: lexical/BM25 или добор доков по пути файла (наш День 32,
  а также Болдырев/Pechatkin/Жуков осознанно). Быстро и дёшево (**[Л §15]** <60с, <$0.10/PR).
- **Семантический RAG (эмбеддинги + реранкер) можно держать и в CI**, если снять латентность
  **кэшем индекса** (отдельный warm-cache workflow по push в доки: Визгин 207с→0.2с). Тогда нет причины
  его выключать. Антипаттерн потока: RAG есть в репо, но на боевом PR выключен (`--rag-mode=off`).

## 8. Метрики и тест пайплайна
**[Л §15]** Latency P50/P95/P99 (<60с), Cost (<$0.10/PR, alert при скачке), Quality (палец вверх/вниз,
>80% полезных), Reliability (>95% без вмешательства).
**[Л §16]** **Golden set** — 10–20 старых PR с известными багами → регресс после правки промпта
(это НАШ приём Дней 22/24). **Smoke test** — запускается ли, не пусто ли, валиден ли формат.

## 9. Безопасность CI (прод-грейд — знать, что есть; сольному репо не нужно)
- **[brief]** `pull_request` из форка → токен read-only, секреты недоступны (защита). «Чинят» через
  `pull_request_target` — и открывают дыру «pwn request»; правильно — checkout по `base.sha`,
  `persist-credentials: false`, чужой код трогать только как ДАННЫЕ, не запускать.
- **[поток]** анти-prompt-injection (diff/доки помечать как недоверенные, nonce-делимитеры),
  маскировка секретов в diff до отправки в облако, fork-PR guard.

## 10. Провайдер и структурный вывод
- В облаке локальной модели (LM Studio/Ollama) НЕТ → цепочка fallback только облачная (наш День 32:
  DeepSeek→OpenRouter).
- Контракт — `response_format={"type":"json_object"}` + шаблон + разбор кодом. Строгий `json_schema`
  провайдеры не держат (наша грабля Дня 24; в потоке на ней же спотыкались — Соловьев/Верушкин ручным
  парсингом ```json```-заборов).

## 11. Частые грабли потока (чего избегать)
1. Нет retry/fallback → сбой модели валит весь CI (частый дефект даже у сильных).
2. «RAG», который не retrieval (чтение всех доков / keyword-overlap; чанки не подаются в ревью).
3. RAG в коде есть, но на PR выключен.
4. Не автоматизация: ручной CLI / запуск из приложения / не постит назад.
5. Ручной парсинг вместо `json_object`.
6. `git diff --stat` вместо содержимого (модель не видит код).
7. Закоммиченные секреты/артефакты (`.env`, `tokens.json`) — проверять перед пушем.
8. «AI» номинально (regex-правила + декоративная модель).
