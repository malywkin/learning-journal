Цепочка из трёх MCP-инструментов

День 17 — агент сам решал, позвать ли один инструмент. Сегодня инструментов три, и они идут цепочкой: получить → обработать → сохранить. Вопрос дня — кто держит порядок: код по рецепту (жёсткий пайплайн) или модель, что решает на ходу (агент). Сервер с инструментами один и тот же — меняется только оркестратор.

Прогони оба режима. Работа у обоих почти одна — сводку всё равно пишет модель. Наценку агента видно в рулении: и лишние походы, и токены на них. Причём токены руления раздуты — каждый поход тащит на вход всю растущую историю (та самая боль Дня 8).

Под капотом В самом протоколе MCP нет «цепочки» и нет вызова инструмента из инструмента — он лишь отдаёт три отдельных инструмента. Порядок задаёт оркестратор снаружи: код (пайплайн) или модель (агент). Передача между шагами надёжна, потому что у каждого инструмента объявлен контракт выхода: возвращаем Pydantic-модель → FastMCP кладёт данные в structuredContent по outputSchema, и следующий шаг берёт поле posts по имени, а не парсит текст. Голый dict такого контракта не даёт — проверено вживую.
А как по-взрослому 1) Передавать между шагами ссылку на данные (id/ресурс), а не сырой текст — иначе цепочка раздувает контекст (антипаттерн «#1 hidden cost»). 2) Вершина 2026 — code execution с MCP: агент не дёргает инструменты по одному, а пишет код, что зовёт их как функции; промежуточное живёт в переменных, не в модели (экономия токенов в разы). 3) Способ «инструмент думает сам внутри сервера» через sampling депрекейтнут (SEP-2577) — вместо него сервер сам зовёт LLM-провайдера.
