# День 19 — Композиция MCP-инструментов (шпаргалка)

Тема: соединить несколько MCP-инструментов в цепочку `search → summarize → save_to_file`
(получить → обработать → сохранить). Главный вопрос дня — **кто держит порядок цепочки**.

Сквозной мост: День 17 — агент сам решал, позвать ли **один** инструмент. День 18 — инструмент
ставил фоновую работу. День 19 — инструментов **три**, и они идут цепочкой. Сервер тот же —
меняется только оркестратор.

---

## Что собрано (всё проверено вживую)
- `arctic.py` — вендорная копия твоего reddit-клиента (Arctic Shift, без ключей).
- `tools.py` — три «работы»: `search_reddit` (поиск, компактный список), `summarize_posts`
  (LLM-сводка, temp 0, запрет выдумывать, ретрай на 429), `save_to_file` (запись в `output/`).
- `mcp_server.py` — FastMCP, три инструмента `search / summarize / save_to_file` с
  **типизированным выходом** (Pydantic → `outputSchema` + `structuredContent`).
- `pipeline.py` — **жёсткий пайплайн**: порядок ведёт КОД, выход одного руками подаётся на вход
  следующего, ошибка на шаге останавливает цепочку.
- `agent.py` — **агент-оркестратор**: тот же tool-calling цикл Дня 17, но модель сама собирает
  цепочку (`tool_choice=auto`).
- `app.py` + `index.html` — тёмная витрина: переключатель пайплайн/агент, лента шагов, видимая
  передача данных, табло «цена гибкости». `run.py` — единый запуск (:8030, MCP на :8029).
- `task19.py` — CLI (`--mode pipeline|agent`).

---

## Три узла (суть, без зубрёжки)

### 1. Цепочку держит ОРКЕСТРАТОР, а не протокол
- В самом **MCP нет «цепочки»** и нет вызова инструмента из инструмента. Он отдаёт три
  отдельных кнопки. Порядок задаёт кто-то снаружи — это и есть оркестратор.
- Это та же форма, что в Дне 18: там в MCP не было **расписания**, тут нет **цепочки**.
  Протокол — минимальный кирпич; «умное» живёт в твоей обвязке.
- Два оркестратора на один и тот же сервер:
  - **Жёсткий пайплайн** (код) — порядок прошит. Так и надо, когда шаги известны заранее
    (методичка Anthropic: «если B требует выход A, а C — выход B, это пайплайн, и он проще
    и дешевле оркестратора»). Наш `search→summarize→save` — ровно такой.
  - **Агент** (модель, `tool_choice=auto`) — порядок выбирает модель. Нужен, когда путь
    нельзя захардкодить. Для известной цепочки это перебор.

### 2. Цена гибкости — замеряли, не на словах
Одна и та же цепочка, один и тот же результат:

| | вызовов LLM | решений модели | кто ведёт порядок |
|---|---|---|---|
| Жёсткий пайплайн | **1** | **0** | код |
| Агент сам | **4** | **3** | модель |

Агент платит лишними вызовами модели за то, что решает порядок сам. Каждый его ход — отдельный
вызов LLM, и на каждом он может ошибиться (не тот порядок, потерял данные). Поэтому для
предсказуемой цепочки берут пайплайн, а агента — где реально нужна гибкость.

### 3. Передача данных = типизированный контракт
- «Второй обрабатывает данные первого» — значит выход `search` должен надёжно лечь на вход
  `summarize`. Надёжно — это **не парсить текст**, а брать поле по имени (`r["posts"]`).
- Чтобы так было, у инструмента объявлен **контракт выхода**: возвращаем Pydantic-модель →
  FastMCP выводит `outputSchema` и кладёт данные в `structuredContent` (спека MCP 2025-06-18).
- **Грабля, пойманная вживую:** голый `-> dict` контракта НЕ даёт — `structuredContent` пуст,
  данные приходят сырым текстом. Форму надо объявить явно (модель/схема).
- Ошибка на шаге останавливает цепочку: сломанный выход нельзя подавать дальше (иначе
  `save_to_file` запишет пустоту).

## А как по-взрослому (лестница зрелости)
1. **Передавать ссылку, а не сырьё.** На объёме гнать полный текст между шагами через модель —
   антипаттерн («#1 hidden cost»). Зрелее: шаг кладёт данные, дальше идёт лёгкий id/ресурс.
2. **Code execution с MCP** (вершина 2026): агент не дёргает инструменты по одному, а пишет
   код, что зовёт их как функции; промежуточное живёт в переменных, не в контексте модели —
   экономия токенов в разы (Anthropic, Cloudflare Code Mode).
3. **`sampling` депрекейтнут** (SEP-2577): способ «инструмент сам думает внутри сервера» уходит,
   замена — сервер сам зовёт LLM-провайдера (у нас — OpenRouter из кода). Строить на нём не надо.
